# LEDs2RAVE4 / Lunchbox Dream LED

> **Status**: Minimally verified SPOTLED generation, plus official multi-frame capture
> **Protocol**: BLE (three incompatible controller generations)
> **Manufacturer**: SPLED / Host No.4 Technology / Shenzhen I-ledshow

## Choose the controller first

These panels are not one protocol. Identify the design app and GATT service
before choosing a client.

| Generation | Design app | Controller / protocol |
|------------|------------|-----------------------|
| Dream LED Skin v1 | LED CHORD (`com.spled.pzse`) | SP107E, `0xFFE0` |
| Dream LED Skin 2.0 | SPOTLED (`com.led.spotled`) | Matrix panel, `0xFF20` |
| Dream Skin 3.0 early | SPOTLED | Matrix panel, `0xFF20` |
| Dream Skin 3.0 recent and future | iLEDColor (`com.led.iledcolor`) | Separate A950 protocol |

For DreamPanel v3, a horizontal serial-number display selects **iLEDColor**;
vertical selects **SPOTLED**. The tested iLEDColor unit had no FF20 service and
is documented in [iLEDColor LED Matrix Panels](iledcolor-led-panel.md). The v1
skin is an SPI pixel-strip product; later products are matrix panels whose
geometry must be queried, not inferred from marketing counts.

## Hardware validation

| Property | Value |
|----------|-------|
| v1 controllers | SP107E / SP110E, source-derived tables |
| SPOTLED test unit | 96×16 RGB888, advertised frames 20, receive window 7280 bytes |
| iLEDColor test unit | 32×64, separate spec |
| Radio | BLE |
| Power | External USB power bank |

This project completed all three SPOTLED information queries and static /
single-frame native-scroll uploads on 2026-11-07/08. A supplied 2026-11-10
official-app capture then confirmed one- and three-frame RGB888 uploads,
visible RGB order and receive-window resume. Those captures were analysed,
not generated by our client. Arbitrary frame counts, other geometry, SP107E
and SP110E remain unverified.

## SPOTLED protocol

The canonical reference is [SPOTLED LED Panels](spotled-led-panel.md). The
Lunchbox legacy service map is:

| UUID | Role | Live properties |
|------|------|-----------------|
| `0000ff20-0000-1000-8000-00805f9b34fb` | SPOTLED service | Confirmed |
| `0000ff21-0000-1000-8000-00805f9b34fb` | Commands and responses | Write without response, notify |
| `0000ff22-0000-1000-8000-00805f9b34fb` | Bulk data | Write without response |
| `0000ff10-0000-1000-8000-00805f9b34fb` | OTA service | Reported; see canonical spec |

1. Connect and enable FF21 notifications through the GATT client.
2. Send Version `04 10 00 00`, DisplayInfo `04 12 00 00` and BufferSize
   `04 14 00 00`, awaiting response types 17, 19 and 21.
3. Use DisplayInfo geometry and the receive-capacity notification; do not issue
   an ATT read or write descriptor bytes to FF21 itself.

Uploads use a 15-byte data header and typed records on FF22. Writes may not
exceed `MTU − 3`, but the official app chose 182-byte chunks at MTU 512. Start
succeeds with type 2 and finish with **type 4**, both status zero. Resume from
the device-driven ContinueSending offset: the official three-frame transfers
paused at exactly 7280 bytes and completed at 13902 bytes. PauseSending type
254 alone does not diagnose MTU.

Earlier custom-client three/eight-frame attempts failed, but the official path
proves three-frame RGB works. Their byte-level difference and the advertised
20-frame guarantee remain open. Static and animated decoded images from the
official capture match the physical panel.

## SP107E / SP110E commands

All commands are four bytes `[d0] [d1] [d2] [cmd]` on `0xFFE1`. These tables
remain source-derived rather than live-verified.

### SP107E

| Command | Bytes | Description |
|---------|-------|-------------|
| Power on | `00 00 00 aa` | Turn on |
| Power off | `00 00 00 bb` | Turn off |
| Set colour | `rr gg bb 0c` | Static RGB; `0x04` is colour order, not static colour |
| Set brightness | `vv 00 00 0a` | 0–255 |
| Set effect | `vv 00 00 08` | 1–180 dynamic, 181 static |
| Set speed | `vv 00 00 09` | 1–186 |
| Set sensitivity | `vv 00 00 13` | Audio gain |
| Query status | `00 00 00 02` | 26 bytes in two packets |

### SP110E

| Command | Bytes | Description |
|---------|-------|-------------|
| Power on | `00 00 00 aa` | Turn on |
| Power off | `00 00 00 ab` | Turn off |
| Set colour | `rr gg bb 1e` | Static RGB |
| Set brightness | `vv 00 00 2a` | 0–255 |
| Set effect | `vv 00 00 2c` | 1–120 dynamic, 121 static |
| Set speed | `vv 00 00 03` | **0–255**, not the SP107E range |
| Query status | `00 00 00 10` | 12-byte reply |

Real SP110E hardware uses FFE0/FFE1. The older assignment of its opcodes to the
FF20 SPOTLED transport was a misattribution.

## Discovery, pairing and reset

Known name prefixes are `SP1`, `LBXDRMSKIN_LED_` and `SpotLED_`. FF20 identifies
SPOTLED when advertised; some short samples contain only `0x1812`, which is a
shared HID service and must not be matched alone. Confirm GATT after connecting.

No account or network provisioning is needed. Bondless SPOTLED clients work.
The official app can optionally initiate legacy Just Works pairing; the panel
responds No Bonding/no LTK and the phone enables encryption for that connection.
There is no persistent bond or PIN, but it is inaccurate to say pairing never
occurs. Other controller generations remain source-derived.

No factory-reset procedure is established. Power-cycling drops a connection but
is not a factory wipe. Rebinding is a fresh scan after closing the old central.

## Open questions

- Live verification of SP107E/SP110E commands and properties.
- The custom-client multi-frame serialization difference and advertised
  20-frame guarantee.
- SPOTLED OTA wire compatibility/recovery, AE30, other geometries, text/font
  records, settings writes and reset behavior.
- iLEDColor settings beyond its separately documented Connect/TestPass and
  upload flows.
