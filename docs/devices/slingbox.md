# Sling Media Slingbox (Solo, Pro, Pro-HD, 240, 350, 500, M1, M2)

> **Status**: Spec Available (unverified)
> **Protocol**: LAN (UDP 5004 discovery broadcast; binary control protocol and ASF stream on one TCP port, 5001 or 5201 by default)
> **Manufacturer**: Sling Media (DISH)
> **Manufacturer Status**: Shutdown. Sling's servers went offline on 2022-11-09.

## Overview

A Slingbox encodes a TV source and streams it to a remote player, and its IR
blaster drives the set-top box. When Sling shut its servers down, SlingPlayer
could no longer log in or find boxes. The boxes themselves still accept
direct connections on the LAN. This spec describes that local protocol: how
to find a box, log in with its admin password, set up the session key,
choose the input and the stream quality, send remote-control buttons and
open the video stream. It is drawn from four open clients:
[Slinger](https://github.com/GerryDazoo/Slinger),
[SlingboxLib](https://github.com/Stonyx/SlingboxLib),
[slingboxstream-py](https://github.com/yeahok/slingboxstream-py) and
[Blingsox](https://github.com/Nomkid/Blingsox).

> **Security**: the login that carries the admin password is encrypted only
> under a TEA key that every open client hard-codes, so anyone who captures
> it can read the password. A client holding the password can also kick the
> current viewer off. Keep the box's port off the internet; use a VPN.
>
> **Left out on purpose**: how to decrypt the video payloads. Above 320x240
> the older boxes (and the Pro-HD at every resolution) encrypt the stream,
> and the 350 can serve AES-encrypted HLS. The open clients implement the
> decryption. The project backlog puts it behind a DMCA 1201 review, so this
> spec does not transcribe it. Sling's IR code database is not reproduced
> either. The spec names only the button numbers a client sends.

## Initial Setup

| Property | Value |
|----------|-------|
| Setup required | No, for a box that was set up while Sling's servers ran |
| Method | `wired`: discover, open the control connection, log in as `admin` |
| Discovery | 32-byte probe (`0101 0000 0200` then zeros) broadcast to UDP 5004; 124-byte reply with product id, finder id, UTF-16LE name and control port |
| Credentials | The admin password, at most 16 characters |
| Passphrase protection | not_applicable |
| Confidence | medium |

On the 500 and M1, Sling's setup gave the box a random 15-character admin
password that the owner never saw. It was stored in the owner's Sling account
as `E1:` plus hex: the UTF-16LE password, TEA-encrypted under the fixed key.
Slinger accepts that form. Slinger's author reports that a 500 or M1 whose
setup never reached Sling's servers keeps `admin` as its password.

**Factory reset**: the reset button is on the back and may be recessed. On
the 350, 500, M1 and M2, hold it with the box powered on until the network
light flashes twice quickly, which can take up to about a minute (one M1
owner needed over 40 s, another never got a reset). On the older models,
hold it until the Sling logo light blinks. A 500 can take ten minutes or more
to finish. The reset erases the name, password, inputs and the IR code set.
Setting the box up again used Sling's servers. Owners reported after the shutdown that
SlingPlayer for desktop 5.0.0 (build 83) with a new Sling account still finished the
job, but that is unconfirmed. A short press or a power cycle only restarts
the box.

**Rebinding to a new network**: on Ethernet the box takes a DHCP address
and comes back by itself; find it again with the broadcast. A 500 on Wi-Fi
has no documented local way to change networks, so use a cable.

## Pairing

| Property | Value |
|----------|-------|
| Pairing required | Yes (admin password in the login message) |
| Security mode | `app_layer` |
| Bonding | `none` |
| PIN source | `user_chosen` (generated by Sling's setup on the 500 / M1) |
| One client at a time | Yes. A second client takes over with message 0x93 |
| Confidence | medium |

There is no per-client credential, so nothing can be unpaired. Changing the
password needs Sling's setup software, or a factory reset.

## Protocol Summary

**Connections.** Open TCP to the control port and send
`GET /stream.asf HTTP/1.1`, `Accept: */*` and
`Pragma: Sling-Connection-Type=Control, Session-Id=0`, then a blank line. The
box sends no HTTP response, only binary messages from then on. For video,
open a second connection and send the same line with
`Sling-Connection-Type=Stream, Session-Id=<session id>`. The box answers with
an ASF stream.

**Message header**, 32 bytes, little-endian:

| Offset | Size | Field |
|--------|------|-------|
| 0 | 2 | Message type, 0x0101 |
| 2 | 2 | Session id (0 on login; then the value the box returned) |
| 4 | 2 | Message id |
| 8 | 2 | Sequence number |
| 12 | 2 | Status (in replies: 0 OK, 2 wrong password) |
| 16 | 2 | Payload length (a multiple of 8) |
| 18 | 2 | Cipher mode: 0x2000 fixed key, 0x8000 session key |
| 24 | 2 | Parity: XOR of the plaintext payload bytes in mode 0x8000 |

**Encryption.** Payloads are TEA (32 cycles, delta 0x9E3779B9) in ECB mode
over little-endian word pairs. Login and the key exchange use a fixed key
that every open client carries. After the key exchange (0xC6), the session
key comes from the client's 16 random bytes, the box's 16-byte challenge and
the session id, through a bit-rotation mix that the spec writes out step by
step. SlingboxLib skips the exchange on the older boxes.

**Sequence.** Login (0x67), key exchange (0xC6), start session (0x7E; a
non-zero status means the box is in use), select input (0x85), 0xA6, stream
settings (0xB5: resolution 0-16, frame rate, 50-8000 kbit/s video,
smoothness, key-frame interval, audio bitrate), then the stream connection.
Send a keep-alive (0x66) every 10 s, and logout (0x68) at the end. IR
buttons (0x87) carry a button number from 1 to 81: 4 is channel up, 9-18
are the digits, 35 is guide. The box maps each number to the code set it
was set up with. The Pro-HD's tuner takes a direct channel number (0x89).

The newer boxes also answer an HTTP/XML API on the same port, guarded by an
MD5 digest header. Blingsox, an unfinished client, uses it to read device
information. The spec records it as a hypothesis.

`scripts/test_slingbox_spec.py` rebuilds every example frame in the spec from
the stated rules, with an invented password, session id, client random and
box challenge. It checks the session-key rule against a second, independent
transcription.

See `device-specs/devices/slingbox.yaml` for the full spec.
